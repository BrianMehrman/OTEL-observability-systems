Kubernetes: OTEL Operator,
DaemonSet & Auto-Instrumentation

How to deploy OTEL natively in Kubernetes — using the Operator to manage Collectors and inject instrumentation into pods without touching application images.

The OTEL Operator — Two CRDs
OpenTelemetryCollector

Declares a Collector deployment. The Operator creates the underlying Deployment, DaemonSet, or Sidecar automatically — no need to write those manifests by hand.

mode: daemonset mode: deployment mode: sidecar replicas resources
Instrumentation

Declares auto-instrumentation config (endpoint, sampler, propagators, per-language env vars). Referenced by pod annotations to inject instrumentation at admission time.

python nodejs java go (eBPF)
Installation
01

Install cert-manager (prerequisite)

The Operator uses admission webhooks which require TLS certificates. cert-manager provisions them automatically.

kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml

kubectl wait --for=condition=Available deployment --all -n cert-manager --timeout=120s
02

Install the OTEL Operator

Deploys the Operator controller and registers the CRDs in the cluster.

kubectl apply -f https://github.com/open-telemetry/opentelemetry-operator/releases/latest/download/opentelemetry-operator.yaml
03

Verify

kubectl get pods -n opentelemetry-operator-system
# NAME READY STATUS
# opentelemetry-operator-xxxxxxxxx-xxxxx 2/2 Running
Collector Deployment Modes
DaemonSet
mode: daemonset

One Collector pod per node. Receives traffic from all pods on that node, attaches k8s metadata, forwards to gateway.

  • Per-node buffering and metadata enrichment
  • Low-latency local collection
  • k8sattributes processor reads local k8s API
  • Forwards upstream via OTLP
Deployment (Gateway)
mode: deployment

Scaled deployment. Handles expensive operations: tail sampling, PII scrubbing, fan-out to final backends.

  • Horizontally scalable (HPA supported)
  • Tail-based sampling requires consistent routing
  • Routes per signal to separate backends
  • Use loadbalancingexporter from agents
Sidecar
mode: sidecar

Injected into each pod as a container. For pods that need pod-local buffering or direct Collector access.

  • Injected via pod annotation
  • Runs in the same pod network namespace
  • Highest isolation; highest resource cost
  • Forwards to DaemonSet or gateway

Auto-Instrumentation Injection

The Instrumentation CRD defines what gets injected. Pod annotations tell the Operator which pods to target and in which language.

apiVersion: opentelemetry.io/v1alpha1
kind: Instrumentation
metadata:
  name: otel-instrumentation
  namespace: my-app
spec:
  exporter:
    endpoint: http://otel-agent-collector:4317
  propagators: [tracecontext, baggage]
  sampler:
    type: parentbased_traceidratio
    argument: "0.1"
Language Pod Annotation Notes
Python instrumentation.opentelemetry.io/inject-python: "my-app/otel-instrumentation" Injects opentelemetry-distro init container
Node.js instrumentation.opentelemetry.io/inject-nodejs: "my-app/otel-instrumentation" Injects @opentelemetry/auto-instrumentations-node
Java instrumentation.opentelemetry.io/inject-java: "my-app/otel-instrumentation" Injects opentelemetry-javaagent.jar via JAVA_TOOL_OPTIONS
Go instrumentation.opentelemetry.io/inject-go: "my-app/otel-instrumentation" eBPF-based — requires Linux kernel ≥ 5.4 and privileged pod
Agent DaemonSet Config (abridged)
apiVersion: opentelemetry.io/v1alpha1
kind: OpenTelemetryCollector
metadata:
  name: otel-agent
  namespace: observability
spec:
  mode: daemonset
  resources:
    limits:
      cpu: 200m
      memory: 256Mi
  config: |
    processors:
      k8sattributes:
        extract:
          metadata:
            - k8s.pod.name
            - k8s.namespace.name
            - k8s.deployment.name
            - k8s.node.name
    exporters:
      loadbalancing:
        resolver:
          k8s:
            service: otel-gateway-collector  # routes by trace_id
Gateway Deployment Config (abridged)
spec:
  mode: deployment
  replicas: 3
  resources:
    limits:
      cpu: 1000m
      memory: 2Gi
  config: |
    processors:
      tail_sampling:
        decision_wait: 10s
        policies:
          - name: errors-always
            type: status_code
          - name: slow-always
            type: latency
          - name: baseline
            type: probabilistic
            probabilistic: {sampling_percentage: 10}
    exporters:
      otlp/tempo:
        endpoint: tempo:4317
      prometheusremotewrite:
        endpoint: http://prometheus:9090/api/v1/write
      loki:
        endpoint: http://loki:3100/loki/api/v1/push
Resource Sizing Guidelines
TierCPU requestCPU limitMemory requestMemory limit
DaemonSet agent50m200m64Mi256Mi
Gateway (per replica)250m1000m512Mi2Gi
Sidecar25m100m32Mi128Mi
Tail sampling constraint: All spans for a given trace must arrive at the same gateway replica. Use the loadbalancingexporter in the agent tier to route by trace_id — do not use a round-robin load balancer on the gateway service for the traces pipeline.

cert-manager installed and all pods Ready
OTEL Operator installed and running
observability namespace created
DaemonSet OpenTelemetryCollector applied
Gateway OpenTelemetryCollector applied (mode: deployment)
RBAC ClusterRole + ClusterRoleBinding for k8sattributes applied

Spans visible in backend with k8s.pod.name and k8s.namespace.name attributes
