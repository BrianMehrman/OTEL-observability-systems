// 02 — The Three Signals

Traces, Metrics & Logs
— what each one is for

All three signals are complementary. You need all three to fully understand a production system. This section covers what each one captures, when to use it, and how they connect to each other.

Deep Dive Per Signal

A trace tracks a single request as it flows through your system. It answers: "Where did this request go, how long did each step take, and where did it fail?"

Example: POST /checkout — trace across 4 services (total 412ms)

The diagram above shows a waterfall view. The root span is the full request. Child spans are nested operations. You can immediately see that the Stripe call is the slowest step and the source of the error.

When to add a manual span: Auto-instrumentation covers HTTP calls, DB queries, and queue operations. Add manual spans when you want visibility into business logic — e.g. validatePromoCode() , calculateTax() , or anything that takes meaningful time or can fail.

Metrics are numbers collected over time. They're cheap to store, fast to query, and ideal for dashboards and alerting. They answer: "Is the system healthy right now?"

Counter

A value that only ever goes up. Reset to zero on restart.

Use for: totals and rates
http.server.request.count db.query.count errors.total messages.published

Gauge

Current value at a point in time. Can go up or down.

Use for: current state
db.pool.connections.active queue.messages.pending memory.heap.used cpu.utilization

Histogram

Samples observations into configurable buckets.

Use for: latency percentiles
http.server.request.duration db.query.duration message.processing.time cache.lookup.duration
Attributes (dimensions) — what makes metrics powerful

Without attributes, a metric like http.request.duration is a single number. With attributes, you can slice it by service, endpoint, status code, region — turning one metric into thousands of specific answers.

http.request.duration{service="order-service", method="POST", status="200", region="eu-west"}
http.request.duration{service="order-service", method="POST", status="500", region="eu-west"}
http.request.duration{service="payment-service", method="POST", status="402", region="us-east"}
Cardinality warning: High-cardinality attributes (user IDs, request IDs) will create millions of unique time series and can overload a metrics backend. Use traces for high-cardinality data. Use metrics for low-cardinality dimensions only.

Logs are timestamped, structured records of events. You almost certainly have them already. OTEL's contribution is adding trace context — so a log entry can be linked back to the exact request that produced it.

Without OTEL context
2024-03-01 10:00:00.320 [ERROR] Payment charge failed: card_declined
2024-03-01 10:00:00.321 [ERROR] Returning 402 to client

// Which user? Which request? Which trace?
// You have no way to connect this to other
// logs or to the trace that caused it.
With OTEL context
2024-03-01T10:00:00.320Z ERROR
message: "Payment charge failed: card_declined"
service.name: "payment-service"
trace_id: abc123def456…
span_id: f9a2b1c3…
user_id: "usr_8821"
order_id: "ord_4492"

The trace_id and span_id in the log entry are the same values present in the trace. Any observability backend with log-trace correlation can jump directly from this log entry to the full request waterfall.

When to Use Which Signal
Signal Question it answers Strengths Limitations Good example use cases
Traces Why was this request slow or broken? Full request context, causality, timing across services High volume = high cost. Can't aggregate across many requests easily Debugging a slow API call, finding which service in a chain errored
Metrics Is the system healthy right now? Cheap, fast, aggregatable, great for alerting No per-request context. High cardinality kills performance p99 latency dashboards, error rate alerts, capacity planning
Logs What exactly happened during an event? Rich detail, free-form, already familiar to developers Expensive at high volume. Hard to query without structure Reading the exact error message and stack trace for a failed request
How the Three Signals Connect

The real power of OTEL comes from linking all three signals around the same trace_id. A single incident investigation flow typically moves through all three.

① Metric fires an alert

error.rate > 5% triggers a PagerDuty alert at 10:03am. You know something is wrong but not what.

② Traces reveal the cause

Filter traces by status=ERROR in the 10:00–10:05 window. The waterfall shows the Stripe span failing at 200ms for 12% of requests.

③ Logs give the detail

Click the failing span's trace_id to jump to correlated logs. The log message reads: "card_declined: insufficient_funds".

trace_id ties all three together — one value links metric → trace → log
This workflow — alert on metrics, investigate with traces, read the detail in logs — is the standard OTEL investigation pattern. It only works when context propagation is set up correctly (covered in Section 05).
