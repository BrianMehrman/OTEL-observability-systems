OpenTelemetry — What it is
and how it fits together

A high-level map of OTEL's components, from a single-service app to a large distributed system. Start here before diving into configuration.

The Three Signal Types

Traces

A trace follows a single request as it moves through your system. Each step is a span. Together they show you where time was spent and where failures occurred.

TraceID SpanID parent_span duration_ms status_code

Metrics

Numerical measurements over time — counters, gauges, histograms. Good for dashboards and alerting. They're cheap to store and fast to query.

http.request.duration db.pool.active queue.depth error.rate

Logs

Timestamped text records. You likely already have these. OTEL adds context — attaching trace and span IDs so logs can be linked back to a specific request.

severity trace_id span_id resource attrs

Inside the Collector — Receive → Process → Export

The Collector is a standalone process (or set of processes). Every piece of telemetry passes through this three-stage pipeline. Understanding these stages is key to configuring OTEL well.

① Receivers

  • otlp/grpc
  • otlp/http
  • prometheus
  • jaeger
  • zipkin
  • hostmetrics
  • k8s events
→

② Processors

  • batch
  • memory_limiter
  • attributes
  • filter
  • tail_sampling
  • transform
  • resourcedetection
→

③ Exporters

  • otlp (backend)
  • prometheus
  • jaeger
  • datadog
  • logging (debug)
  • file
  • kafka
Note on processors: The batch processor is almost always required — it prevents flooding backends with individual spans. The memory_limiter is equally important; without it, a traffic spike can OOM your collector.
Sampling — The Volume Problem

Head-based sampling

The decision to record a trace is made at the start of the request. Simple and low overhead, but you cannot guarantee capturing error traces — the decision happens before you know if the request will fail.

Good fit → small/medium apps

Tail-based sampling

The Collector buffers spans and makes the decision after the trace is complete. You can define rules: always keep errors, slow requests, or traces from specific users. More complex, requires stateful collector.

Good fit → large / high-volume apps
Six Decisions That Shape Your Setup
01

Auto vs. Manual instrumentation

Auto-instrumentation covers HTTP, DB, queues with no code changes. Add manual spans for business logic that matters — checkout, payment, etc.

02

Direct export vs. Collector

Small apps can export directly from the SDK to a backend. Add a Collector once you need sampling, PII scrubbing, or routing to multiple destinations.

03

Agent vs. Gateway collector

Agents run per node and handle local buffering. Gateways run centrally and handle expensive operations. At scale you need both.

04

Sampling strategy

100% sampling is fine at low volume. At high volume, tail-based sampling with error-always rules gives you coverage without the storage cost.

05

Context propagation

In a distributed system, trace context must cross service boundaries via HTTP headers (W3C TraceContext). Every service must read and forward these headers.

06

Backend choice

OTEL is vendor-neutral. One backend (Grafana Cloud, Datadog) is simplest. Separate backends per signal type is common at platform scale.
