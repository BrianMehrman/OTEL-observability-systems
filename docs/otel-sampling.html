Sampling
— control volume without losing signal

At low traffic, record everything. As volume grows, storing every trace becomes expensive fast. Sampling is how you stay within budget while guaranteeing you never miss an error or a slow request.

The Volume Problem

A single service at modest scale generates significant trace volume. At distributed system scale, naive 100% sampling is unworkable.

The goal: keep 100% of interesting traces (errors, slow requests, specific users) and drop a configurable percentage of healthy, fast, routine traffic — which tells you nothing new.
Two Approaches — Head vs. Tail Sampling
HEAD-BASED Decide at request start

The SDK flips a coin when a new trace starts. If it decides to sample, all spans in that trace are recorded. If not, none are. The decision is locked in before anything happens.

1
Request arrives at the root serviceSDK generates a trace_id
2
SDK makes a random sampling decisione.g. keep 10% of all requests
3
Decision is encoded in the trace contextPropagated to all downstream services
4
All services honour the same decisionEither the whole trace is kept, or none of it
PROS
  • Zero latency overhead
  • Simple to configure
  • Stateless — no buffering
  • Works in the SDK, no Collector needed
CONS
  • Blind to outcomes
  • May drop error traces
  • No guarantee of capturing slow requests
TAIL-BASED Decide after trace completes

The Collector buffers all spans for a trace until the trace is complete (or a timeout expires). It then applies policy rules to decide whether to keep or drop the entire trace.

1
All spans arrive at the gateway CollectorBuffered in memory by trace_id
2
Collector waits for trace to completeOr until decision_wait timeout expires
3
Policies evaluate the completed traceStatus, latency, attributes
4
Keep or drop decision applied to all spansEntire trace kept or entirely dropped
PROS
  • Always captures errors
  • Captures slow requests
  • Rich, rule-based policies
  • Can target specific services/users
CONS
  • Requires stateful Collector
  • Memory intensive
  • Spans for a trace must hit same Collector instance

Use head-based when…

Traffic is low to medium (<1K req/s), you want simplicity with no Collector dependency, or you're just getting started and want working traces quickly. Also appropriate when your error rate is so low that missing a few errors is acceptable.

Use tail-based when…

Traffic is high and storage cost matters, you need guaranteed capture of all errors and slow requests, or you need to target specific user segments or services for full trace capture. Requires the two-tier Collector topology from Section 03.

Tail Sampling — Policy Types
status_code
type: status_code

Keep all traces where any span has an error status. This is the most important policy — never drop a broken request.

- name: always-errors
  type: status_code
  status_code:
    status_codes:
      - ERROR
latency
type: latency

Keep all traces where the root span exceeded a latency threshold. Captures slowness even when no error was returned.

- name: slow-requests
  type: latency
  latency:
    threshold_ms: 1000
    # keep anything over 1s
probabilistic
type: probabilistic

Random percentage of healthy traces. Provides a baseline sample of normal traffic for trend analysis and capacity planning.

- name: baseline-sample
  type: probabilistic
  probabilistic:
    sampling_percentage: 5
    # keep 5% of healthy traces
string_attribute
type: string_attribute

Keep traces matching a specific attribute value. Useful for always capturing traces from specific users, tenants, or services.

- name: vip-tenants
  type: string_attribute
  string_attribute:
    key: tenant.tier
    values:
      - enterprise
      - vip
rate_limiting
type: rate_limiting

Cap the number of traces per second flowing through regardless of other policies. Acts as a hard spending limit on your backend.

- name: hard-cap
  type: rate_limiting
  rate_limiting:
    spans_per_second: 500
    # absolute ceiling
composite
type: composite

Combines multiple policies with rate allocation per policy. Lets you say "keep 200 errors/s AND 100 slow traces/s AND 200 random traces/s".

- name: combined
  type: composite
  composite:
    max_total_spans_per_second: 500
    policy_order:
      - always-errors
      - slow-requests
      - baseline-sample
Production-Ready Tail Sampling Config

A complete, layered policy set for a high-volume service. Policies are evaluated in order — first match wins. Errors and slow requests are always kept regardless of volume.

tail_sampling:
  decision_wait:      10s     # wait this long for all spans to arrive
  num_traces:         50000   # max traces buffered in memory at once
  expected_new_traces_per_sec: 1000

  policies:

    ## ── LAYER 1: Always keep — no exceptions ──────────────────
    - name: errors-always
      type: status_code
      status_code: {status_codes: [ERROR]}

    - name: slow-always          # slow traces regardless of status
      type: latency
      latency: {threshold_ms: 2000}

    ## ── LAYER 2: Business-critical paths ──────────────────────
    - name: checkout-always      # keep all checkout/payment traces
      type: string_attribute
      string_attribute:
        key:    http.route
        values: ["/checkout", "/payment", "/order"]

    - name: enterprise-always   # keep all enterprise tenant traces
      type: string_attribute
      string_attribute:
        key:    tenant.tier
        values: [enterprise]

    ## ── LAYER 3: Baseline sample of healthy traffic ────────────
    - name: healthy-sample
      type: probabilistic
      probabilistic: {sampling_percentage: 5}

    ## ── LAYER 4: Hard cap — spending protection ────────────────
    - name: rate-limiter
      type: rate_limiting
      rate_limiting: {spans_per_second: 1000}
Common Pitfalls
01

Spans split across Collector instances

Tail sampling is stateful. If spans from the same trace hit different gateway replicas, the policy sees an incomplete trace and makes a wrong decision.

→ Use trace_id-based consistent hashing on your load balancer
02

decision_wait too short

If your longest operation (e.g. a batch job) takes 30s but decision_wait is 10s, the Collector decides before all spans have arrived — and may drop spans it should keep.

→ Set decision_wait to 2× your p99 trace duration
03

Sampling metrics alongside traces

Sampling only applies to traces. Never apply probabilistic sampling to metrics — you will corrupt your aggregates and break alerting.

→ Metrics pipeline must always use 100% — no sampling processor
