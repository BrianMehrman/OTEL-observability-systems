// 03 — The Collector

The OTEL Collector
— pipeline, config & scale

The Collector is the operational core of any OTEL setup. It sits between your application and your backend, and it's where routing, filtering, sampling, and enrichment all happen. Get this right and everything else becomes easier.

The Three-Stage Pipeline

Every signal — traces, metrics, logs — flows through the same three stages. A Collector can run multiple independent pipelines simultaneously, one per signal type.

Configuration Walkthroughs
Minimal production-ready config — single service, one backend, straightforward setup 
# collector-config.yaml — simple setup

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317   # your app sends here
      http:
        endpoint: 0.0.0.0:4318   # or here (HTTP)

processors:
  memory_limiter:                       # ← always first
    check_interval: 1s
    limit_mib: 400                     # hard memory ceiling
    spike_limit_mib: 100               # headroom for spikes

  batch:                                # ← always last processor
    send_batch_size: 1000             # send after N items
    timeout: 5s                       # or after 5s, whichever first

  resourcedetection:                    # auto-detect host/cloud metadata
    detectors: [env, system, docker]

exporters:
  otlp:
    endpoint: https://your-backend:4317
    headers:
      Authorization: "Bearer ${env:BACKEND_API_KEY}"

  logging:                              # useful during development
    verbosity: detailed

service:
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [memory_limiter, resourcedetection, batch]
      exporters:  [otlp]
    metrics:
      receivers:  [otlp]
      processors: [memory_limiter, resourcedetection, batch]
      exporters:  [otlp]
    logs:
      receivers:  [otlp]
      processors: [memory_limiter, resourcedetection, batch]
      exporters:  [otlp]

⚠ memory_limiter must be first

Processors run in the order listed. memory_limiter must come before anything else so it can drop data before it fills your heap during a traffic spike.

⚠ batch must be last

batch groups items before sending to the exporter. Placing it last ensures all processing is done before grouping. Reversing this order wastes work.

✓ resourcedetection

Auto-attaches host name, OS, cloud provider, and region to every span and metric. Free signal that makes filtering in your backend much easier.

Three separate pipelines

Traces, metrics, and logs are declared as independent pipelines. They share processors here, but you can give each one different rules as needs grow.

Agent config (per node / DaemonSet) — lightweight, close to the app, minimal processing 
# agent-config.yaml — runs on every node in your cluster
# Goal: receive locally, enrich lightly, forward to gateway

receivers:
  otlp:
    protocols:
      grpc: endpoint: 0.0.0.0:4317
  hostmetrics:                          # CPU, memory, disk, network
    collection_interval: 30s
    scrapers:
      cpu:
      memory:
      disk:
      network:

processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 256                     # agents stay lean
    spike_limit_mib: 64

  k8sattributes:                        # attach pod/namespace metadata
    extract:
      metadata: [k8s.pod.name, k8s.namespace.name,
                 k8s.deployment.name, k8s.node.name]
    pod_association:
      - sources:
          - from: resource_attribute
            name: k8s.pod.ip

  resourcedetection:
    detectors: [env, k8snode, system]

  batch:
    send_batch_size: 500
    timeout: 2s                        # lower latency than gateway

exporters:
  otlp:                                 # forward to gateway collectors
    endpoint: gateway-collector:4317
    tls:
      insecure: false

service:
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [memory_limiter, k8sattributes, resourcedetection, batch]
      exporters:  [otlp]
    metrics:
      receivers:  [otlp, hostmetrics]
      processors: [memory_limiter, k8sattributes, resourcedetection, batch]
      exporters:  [otlp]

Agent job: enrich, not decide

The agent's role is to attach Kubernetes context (pod name, namespace, deployment) and forward. It should not do expensive work like tail sampling — that's the gateway's job.

✓ k8sattributes processor

Automatically attaches pod and namespace metadata to every span and metric by reading the Kubernetes API. Without this, your telemetry has no idea which pod it came from.

Gateway config (centralised tier) — receives from agents, samples, routes to multiple backends 
# gateway-config.yaml — centralised, scaled horizontally
# Goal: sample intelligently, scrub PII, route to backends

receivers:
  otlp:
    protocols:
      grpc: endpoint: 0.0.0.0:4317

processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 2000                   # gateway needs more headroom
    spike_limit_mib: 400

  tail_sampling:                        # decision AFTER trace completes
    decision_wait: 10s                 # wait for all spans to arrive
    policies:
      - name: keep-errors               # always keep failed traces
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: keep-slow                 # keep anything over 1 second
        type: latency
        latency: {threshold_ms: 1000}
      - name: sample-healthy            # keep 10% of normal traffic
        type: probabilistic
        probabilistic: {sampling_percentage: 10}

  attributes:                           # scrub PII before exporting
    actions:
      - key: user.email
        action: delete
      - key: http.request.header.authorization
        action: delete
      - key: user.id
        action: hash                   # hash instead of delete

  batch:
    send_batch_size: 2000
    timeout: 10s

exporters:
  otlp/jaeger:                          # traces → Jaeger
    endpoint: jaeger:4317
  prometheusremotewrite:               # metrics → Prometheus
    endpoint: http://prometheus:9090/api/v1/write
  otlp/loki:                            # logs → Loki
    endpoint: loki:3100

service:
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [memory_limiter, tail_sampling, attributes, batch]
      exporters:  [otlp/jaeger]
    metrics:
      receivers:  [otlp]
      processors: [memory_limiter, attributes, batch]
      exporters:  [prometheusremotewrite]
    logs:
      receivers:  [otlp]
      processors: [memory_limiter, attributes, batch]
      exporters:  [otlp/loki]

Named exporters: otlp/jaeger, otlp/loki

You can have multiple exporters of the same type using type/name syntax. This is how you fan out to separate backends per signal from a single gateway.

⚠ Tail sampling requires stateful collector

The gateway must buffer all spans for a trace window (10s here) before deciding. This means all spans for the same trace must route to the same gateway instance.

✓ PII scrubbing at the gateway

Deleting and hashing sensitive attributes centrally means you never have to touch application code to change what gets stored. One config change applies everywhere.

Three backends, one pipeline

Each signal routes to its own backend. Traces go to Jaeger, metrics to Prometheus, logs to Loki. Each team can own their tool without coupling to others.

Topology — Agent vs. Gateway
SMALL Single collector

One Collector instance handles everything. Runs as a sidecar container or on the same host as the app.

Your App → OTLP → Collector → Backend
  • ✓ Simple — one config file
  • ✓ Low operational cost
  • ✓ Collector is optional at very low volume
LARGE Two-tier topology

Agents run per-node (DaemonSet in k8s). Gateways run as a central deployment, scaled horizontally.

Service A Service B Service C
↓ OTLP (localhost)
Agent (node 1) Agent (node 2)
↓ forward
Gateway ×3
↓ route per signal
Jaeger Prometheus Loki
  • ✓ Agents handle local buffering and k8s enrichment
  • ✓ Gateways handle sampling, PII, routing
  • ✓ Gateway tier scales independently from apps
Critical Processors — What They Do
memory_limiter required

Monitors the Collector's memory usage. When it exceeds the limit, it starts dropping data and returning errors to senders. Without this, a traffic spike OOMs the Collector process entirely — taking your entire observability pipeline down.

memory_limiter:
  check_interval:  1s
  limit_mib:       400   # hard limit
  spike_limit_mib: 100   # soft buffer
batch required

Groups spans, metrics, and logs into batches before sending to exporters. Without batching, every individual span triggers a separate network call to your backend — which is both slow and expensive.

batch:
  send_batch_size: 1000  # send at 1000 items
  timeout:         5s    # or every 5s
  send_batch_max_size: 2000
attributes common

Add, update, delete, or hash attributes on spans, metrics, or logs. The primary tool for PII scrubbing and for adding environment context (e.g. adding a deployment.env tag to everything).

attributes:
  actions:
    - key: user.email
      action: delete
    - key: deployment.env
      value:  production
      action: upsert
filter common

Drop entire spans, metrics, or log records based on conditions. Use to suppress noisy health check endpoints or internal polling traffic that clutters your traces.

filter:
  traces:
    span:
      # drop health check spans
      - 'attributes["http.route"] == "/healthz"'
      - 'attributes["http.route"] == "/ready"'
