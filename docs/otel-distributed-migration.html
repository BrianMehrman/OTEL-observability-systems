What Datadog's Inference Does (and What You Must Replace)

⚠ Critical Risk Services with no OTEL instrumentation become completely invisible in SigNoz and Grafana. The service map only shows services that emit spans. Never decommission Datadog for a service until that service has explicit OTEL instrumentation.
Inference Method How Datadog Does It What You Lose Without It OTEL Replacement
Log correlation Injects dd.trace_id into log lines; correlates across services Trace ↔ log linking OTEL SDK injects trace_id into structured logs
APM header passthrough x-datadog-* headers pass through uninstrumented services Request continuity across hops Explicit traceparent header propagation per service
Network Performance Monitoring Tracks TCP connections between hosts to infer topology Service map edges for uninstrumented services Explicit spans per service (no equivalent inference)
Service Entry Inference Infers service entry points from network + log metadata Automatic service discovery service.name resource attribute on every OTEL span
💡 Strategy Run OTEL instrumentation in parallel with Datadog agents for 1–2 weeks per service. Compare the two views. Only remove the Datadog agent when you're confident OTEL coverage is equal or better.

Ruby: Rails + Sidekiq Instrumentation

Rails Web Server

Auto-instruments Puma, Rack, Rails MVC, ActiveRecord, Net::HTTP, Faraday, and all outbound HTTP calls.

opentelemetry-sdk instrumentation-rails instrumentation-active_record

Sidekiq Enterprise

Creates producer span on enqueue, consumer span on processing. Trace context stored in job metadata in Redis.

instrumentation-sidekiq instrumentation-redis instrumentation-bunny

Gemfile

# Gemfile
gem 'opentelemetry-sdk'
gem 'opentelemetry-exporter-otlp'
gem 'opentelemetry-instrumentation-rails'
gem 'opentelemetry-instrumentation-active_record'
gem 'opentelemetry-instrumentation-rack'
gem 'opentelemetry-instrumentation-sidekiq'    # enqueue + process spans
gem 'opentelemetry-instrumentation-redis'      # Redis calls
gem 'opentelemetry-instrumentation-bunny'      # RabbitMQ via Bunny
gem 'opentelemetry-instrumentation-faraday'    # outbound HTTP (Faraday)
gem 'opentelemetry-instrumentation-http'       # outbound HTTP (Net::HTTP)

Initializer — config/initializers/opentelemetry.rb

require 'opentelemetry/sdk'
require 'opentelemetry/exporter/otlp'
require 'opentelemetry/instrumentation/all'

OpenTelemetry::SDK.configure do |c|
  c.service_name    = ENV.fetch('OTEL_SERVICE_NAME', 'rails-web')
  c.service_version = ENV.fetch('APP_VERSION', 'unknown')

  c.resource = OpenTelemetry::SDK::Resources::Resource.create({
    'deployment.environment' => ENV.fetch('DEPLOY_ENV', 'development'),
    'service.namespace'      => 'my-platform',
  })

  c.use_all  # auto-enables all installed instrumentation gems
end

Java: Zero-Code Agent

💡 Easiest Migration Win The Java agent requires zero application code changes. Add the JAR and set environment variables. All Spring Boot, JDBC, Kafka, RabbitMQ, and AWS SDK calls are automatically instrumented.

Docker / Kubernetes — Environment Variables

# docker-compose.yml or Kubernetes Deployment env block
env:
  - name: JAVA_TOOL_OPTIONS
    value: "-javaagent:/opt/otel/opentelemetry-javaagent.jar"
  - name: OTEL_SERVICE_NAME
    value: "java-gateway"
  - name: OTEL_EXPORTER_OTLP_ENDPOINT
    value: "http://otel-collector:4317"
  - name: OTEL_EXPORTER_OTLP_PROTOCOL
    value: "grpc"
  - name: OTEL_TRACES_EXPORTER
    value: "otlp"
  - name: OTEL_LOGS_EXPORTER
    value: "otlp"
  - name: OTEL_RESOURCE_ATTRIBUTES
    value: "deployment.environment=staging,service.namespace=my-platform"

Kubernetes: Auto-Inject via OTEL Operator

# Instrumentation CRD — applies the agent to annotated pods
apiVersion: opentelemetry.io/v1alpha1
kind: Instrumentation
metadata:
  name: java-instrumentation
spec:
  exporter:
    endpoint: http://otel-daemonset-collector:4317
  propagators: [tracecontext, baggage, b3]
  java:
    image: ghcr.io/open-telemetry/opentelemetry-operator/autoinstrumentation-java:latest
---
# Annotate your Deployment — no code changes
metadata:
  annotations:
    instrumentation.opentelemetry.io/inject-java: "true"

Node.js: Snowflake API Instrumentation

Install

npm install \
  @opentelemetry/sdk-node \
  @opentelemetry/auto-instrumentations-node \
  @opentelemetry/exporter-trace-otlp-grpc

tracing.js — Bootstrap File (loaded before app)

const { NodeSDK } = require('@opentelemetry/sdk-node');
const { getNodeAutoInstrumentations } = require('@opentelemetry/auto-instrumentations-node');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-grpc');
const { Resource } = require('@opentelemetry/resources');
const { SemanticResourceAttributes } = require('@opentelemetry/semantic-conventions');

const sdk = new NodeSDK({
  resource: new Resource({
    [SemanticResourceAttributes.SERVICE_NAME]:
      process.env.OTEL_SERVICE_NAME || 'node-snowflake-api',
    [SemanticResourceAttributes.DEPLOYMENT_ENVIRONMENT]:
      process.env.DEPLOY_ENV || 'development',
  }),
  traceExporter: new OTLPTraceExporter({
    url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT || 'http://otel-collector:4317',
  }),
  instrumentations: [getNodeAutoInstrumentations()],
});

sdk.start();
process.on('SIGTERM', () => sdk.shutdown());

package.json

{
  "scripts": {
    "start": "node --require ./tracing.js app.js"
  }
}

Context Propagation Through Your Messaging Layer

⚠ The Hard Part Without explicit context propagation through message brokers, async message flows appear as disconnected traces — no link between producer and consumer. This is the most common gap when migrating away from Datadog inference.

RabbitMQ

opentelemetry-instrumentation-bunny (Ruby) and the Java agent automatically inject W3C TraceContext into AMQP message headers.

No manual code needed — publish and consume normally.

Ruby: instrumentation-bunny Java: agent auto AMQP headers

Kafka

Java agent instruments kafka-clients automatically. Trace context flows via Kafka record headers (traceparent, tracestate).

Node.js: auto-instrumentations-node includes KafkaJS instrumentation.

Java: agent auto Node: kafkajs instr. Record headers

AWS SNS / SQS

Trace context propagates via SQS message attributes. Both Java agent and auto-instrumentations-node handle this automatically via the AWS SDK instrumentation.

⚠ SQS max 10 message attributes — reserve one slot for AWSTraceHeader.

Java: aws-sdk auto Node: aws-sdk instr. MessageAttributes

Redis / Sidekiq

instrumentation-sidekiq serializes traceparent into Sidekiq job JSON stored in Redis. Links web request → enqueue → job execution automatically.

Ruby: instrumentation-sidekiq Job JSON metadata Auto end-to-end

Verifying Propagation

How to check it's working In SigNoz or Grafana Tempo, send a test request and search for the trace. You should see spans with kind=PRODUCER (publish) linked to spans with kind=CONSUMER (process) in the same trace tree. If they appear as two separate traces, the headers are not flowing through the broker.

OTEL Collector Deployment by Platform

EC2 / VM — Docker Sidecar

Run a Collector container alongside each service in docker-compose. All services on the host point to http://otel-collector:4318.

Kubernetes — OTEL Operator DaemonSet

Deploy the OTEL Operator and a DaemonSet Collector (one pod per node). Pods send to the node-local collector. Includes k8sattributes processor.

EC2 Docker Compose

# docker-compose.yml (per service on EC2)
services:
  app:
    image: my-service:latest
    environment:
      OTEL_EXPORTER_OTLP_ENDPOINT: "http://otel-collector:4318"
      OTEL_EXPORTER_OTLP_PROTOCOL: "http/protobuf"
    depends_on: [otel-collector]

  otel-collector:
    image: otel/opentelemetry-collector-contrib:0.96.0
    volumes:
      - ./otel-collector.yaml:/etc/otelcol-contrib/config.yaml
    ports:
      - "4317:4317"   # OTLP gRPC
      - "4318:4318"   # OTLP HTTP

Kubernetes DaemonSet (OTEL Operator)

apiVersion: opentelemetry.io/v1alpha1
kind: OpenTelemetryCollector
metadata:
  name: otel-daemonset
spec:
  mode: daemonset
  config: |
    receivers:
      otlp:
        protocols:
          grpc: { endpoint: 0.0.0.0:4317 }
          http: { endpoint: 0.0.0.0:4318 }
    processors:
      k8sattributes:
        extract:
          metadata: [k8s.namespace.name, k8s.pod.name, k8s.deployment.name]
    exporters:
      otlp/signoz:
        endpoint: "http://signoz-otel-collector.monitoring:4317"
        tls: { insecure: true }

Environment Routing Strategy

💡 Key Principle Application code is identical across all environments. Only the OTEL Collector configuration changes. Set OTEL_EXPORTER_OTLP_ENDPOINT to your local collector — the collector decides where data goes.
Production
Datadog
OTEL SDK→Collector→ Datadog

Unchanged. All traces and logs continue to Datadog via the datadog exporter.

Staging
SigNoz (Persistent)
OTEL SDK→Collector→ SigNoz

One SigNoz instance per staging cluster. Data persists between runs for trend analysis.

Integration (E2E)
SigNoz (Ephemeral)
OTEL SDK→Collector→ SigNoz

Spin up SigNoz with each isolated env. Torn down after E2E tests. Cost = $0 in backend fees.

Test / CI
No-Op
OTEL SDK→ none exporter

Set OTEL_TRACES_EXPORTER=none. No network calls, no cost, fast tests.

Production Collector Config (→ Datadog)

exporters:
  datadog:
    api:
      key: "${DD_API_KEY}"
      site: datadoghq.com
    traces:
      span_name_as_resource_name: true
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch, resource]
      exporters: [datadog]
    logs:
      receivers: [otlp, filelog]
      processors: [batch, resource]
      exporters: [datadog]

Integration Ephemeral Stack (docker-compose)

# docker-compose.integration.yaml — deploy alongside each isolated env
services:
  signoz:
    image: signoz/signoz:latest
    ports: ["3301:3301"]   # UI
    volumes: [signoz-data:/var/lib/signoz]

  otel-collector:
    image: otel/opentelemetry-collector-contrib:0.96.0
    environment:
      SIGNOZ_ENDPOINT: "http://signoz:4317"

Migration Roadmap

1

Log Router — Immediate Cost Win

Deploy OTEL Collector to non-prod environments. Configure filelog receiver + route to SigNoz. Set OTEL_TRACES_EXPORTER=none in test. No application code changes.

Days 1–7 No code changes Immediate cost reduction Low risk
2

Ruby Services — Rails + Sidekiq

Add opentelemetry gems, add initializer, set env vars. Deploy to staging. Parallel-run with Datadog for 1 week. Validate Sidekiq trace chains and RabbitMQ spans.

Weeks 2–3 Gemfile + initializer Parallel run Low risk
3

Java Services — Zero-Code Agent

Add javaagent JAR to Docker images or K8s init containers. Set JAVA_TOOL_OPTIONS. Annotate K8s Deployments for auto-inject. Verify Kafka and Spring AMQP spans.

Weeks 3–4 Dockerfile only K8s annotation Low risk
4

Node.js APIs

npm install OTEL packages, create tracing.js, update package.json start command. Set env vars. Deploy to staging, verify Snowflake API spans link to callers.

Weeks 4–5 package.json + tracing.js Low risk
5

Close Messaging Propagation Gaps

Run end-to-end trace validation. Trace from web request through Sidekiq → RabbitMQ → Java consumer → Kafka → downstream. Verify SNS/SQS flows. Fix any broken trace links.

Weeks 5–6 Validation only Medium risk
6

Decommission Datadog per Service

After each service is validated, remove the Datadog agent from non-prod deployments. Production continues to use Datadog via OTEL Collector. Measure cost savings per environment.

Week 6+ Per-service Cost savings realized Low risk
