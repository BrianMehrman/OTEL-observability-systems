// 05 — Distributed Tracing

Context Propagation
— how traces cross service boundaries

A distributed trace is only possible if every service in the chain passes context to the next. This section covers how that works, what can go wrong, and how to handle async patterns like queues and background jobs.

The Core Idea

A trace spans multiple services. Each service creates spans and passes a small packet of context — the trace context — to every downstream call it makes. Without this, each service records isolated spans with no connection to the others.

Propagation Formats
W3C TraceContext recommended

The IETF standard. Two headers: traceparent carries the trace and span IDs, tracestate carries vendor-specific data. Supported by all OTEL SDKs and most modern APM tools.

traceparent: 00-{traceId}-{spanId}-{flags}
tracestate:  vendor=value

# Example
traceparent: 00-abc123…32chars…def-f9a2b1c3…16chars-01
B3 (Zipkin) legacy

Originated with Zipkin, widely used in older microservice stacks. Two flavours: multi-header (separate headers per field) and single-header. The OTEL SDK supports both for compatibility with existing systems.

X-B3-TraceId:      abc123def456…
X-B3-SpanId:       f9a2b1c3…
X-B3-ParentSpanId: d3e4c5f6…
X-B3-Sampled:      1
Jaeger / AWS X-Ray vendor

Vendor-specific formats. If you're migrating from Jaeger or running on AWS, the OTEL SDK can be configured to read and write these alongside W3C headers during the transition period.

# Jaeger
uber-trace-id: {traceId}:{spanId}:{parentId}:{flags}

# AWS X-Ray
X-Amzn-Trace-Id: Root=1-…;Parent=…;Sampled=1
What Breaks Trace Continuity

Missing headers on outgoing calls

Scenario: custom HTTP client bypasses the SDK

Any HTTP call made with a raw client (e.g. urllib.request or fetch called directly) won't have propagation headers injected. The downstream service starts a new root span.

→ Use the OTEL-instrumented HTTP client, or manually inject headers:

# Python — manual injection
from opentelemetry import propagate

headers = {}
propagate.inject(headers)
requests.get(url, headers=headers)

Third-party service in the call chain

Scenario: external API that doesn't support OTEL

If your app calls Stripe, Twilio, or any external service, that service won't pass context back. The trace ends at your outbound call. This is expected — model it as a leaf span.

→ Add an explicit span wrapping the call with the result metadata:
with tracer.start_as_current_span("stripe.charge") as span:
    span.set_attribute("stripe.charge_id", charge_id)
    span.set_attribute("payment.amount", amount)
    result = stripe.charge(...)
    if result.error:
        span.set_status(StatusCode.ERROR)

Mixed propagation formats

Scenario: migrating from Zipkin/Jaeger to OTEL

An older service emits B3 headers. A newer service only reads W3C headers. The trace breaks at that boundary because neither service understands the other's format.

→ Configure OTEL SDK to accept multiple formats during transition:
# Enable both formats simultaneously
OTEL_PROPAGATORS=tracecontext,baggage,b3multi

# Or in code
from opentelemetry.propagators.composite import CompositePropagator
propagator = CompositePropagator([TraceContextPropagator(), B3MultiFormatPropagator()])

Context lost across thread / async boundaries

Scenario: spawning threads, async tasks, or workers

Trace context is stored in a context object that is thread-local by default. Spawning a new thread or creating an async task without propagating the context creates a new root span.

→ Explicitly attach context when crossing boundaries:
# Python — passing context to a thread
from opentelemetry import context

ctx = context.get_current()  # capture here

def worker():
    token = context.attach(ctx)  # restore here
    try:
        do_work()
    finally:
        context.detach(token)
Async Patterns — Queues & Background Jobs

Message Queue (Kafka, SQS, RabbitMQ)

The producer and consumer are decoupled in time. Context must be serialised into the message headers/attributes and deserialised by the consumer.

# Producer — inject context into message
headers = {}
propagate.inject(headers)
kafka.produce(topic, value=payload, headers=headers)

# Consumer — extract context from message
ctx = propagate.extract(msg.headers)
with tracer.start_as_current_span(
    "process-order",
    context=ctx,
    kind=SpanKind.CONSUMER
) as span:
    process(msg.value)

This creates a link between the producer trace and the consumer trace — the two appear as separate but connected traces in your backend.

Background Jobs & Scheduled Tasks

Scheduled jobs have no incoming request to extract context from. They start new root spans. Enqueue requests can pass context to the job via a job payload field.

# Enqueueing — store context in job payload
headers = {}
propagate.inject(headers)
queue.enqueue(
    "send-invoice",
    payload={"order_id": order_id},
    trace_context=headers  # store as job metadata
)

# Job handler — restore context
ctx = propagate.extract(job.trace_context)
with tracer.start_as_current_span(
    "send-invoice",
    context=ctx
) as span:
    send_invoice(job.payload)
