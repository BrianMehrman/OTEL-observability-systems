Current Stack & Modern Alternatives

An audit of the current Rails log pipeline on EC2 — with three replacement options: two fully self-hosted stacks that eliminate SaaS cost entirely, and a hybrid that keeps Datadog for production while running a free stack for non-production environments.

Pain Points

High EC2 Memory Pressure

Logstash + Elasticsearch are both JVM processes requiring 5–11 GB RAM combined — before your Rails app even starts. This forces larger (more expensive) EC2 instance sizes.

Datadog Host Billing

Datadog charges per host per month. Adding APM (traces) or Infrastructure Monitoring adds additional fees on top of the base host cost. Log ingest is billed separately per GB.

Logs Only — No Traces or Metrics

The pipeline carries only log data. There is no distributed tracing (no request waterfall), no application-level p99 latency or error rate counters, and no OTLP-native telemetry.

Fragile File-Based Pipeline

Log rotation, disk fill, and Logstash crashes create gaps in log history. The file-to-Logstash path has no backpressure mechanism — if Logstash falls behind, logs accumulate on disk.

Key Insight

Rails instrumentation code is identical in all environments. The only difference is one environment variable (OTEL_EXPORTER_OTLP_ENDPOINT) and which OTEL Collector config file is mounted. Developers get full observability locally; production keeps Datadog's incident management and SLO features.

Production Collector Config
# otel-collector-config.production.yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

exporters:
  datadog:
    api:
      site: datadoghq.com     # or datadoghq.eu
      key:  ${DD_API_KEY}

service:
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [memory_limiter, resourcedetection, batch]
      exporters:  [datadog]
    metrics:
      receivers:  [otlp]
      processors: [memory_limiter, resourcedetection, batch]
      exporters:  [datadog]
    logs:
      receivers:  [otlp]
      processors: [memory_limiter, resourcedetection, batch]
      exporters:  [datadog]

Cost Impact
Eliminate Logstash + Elasticsearch

Free 5–10 GB RAM on production EC2. May allow a smaller (cheaper) instance type.

Pay Datadog only for production

Eliminate Datadog host fees for every dev and staging environment. Typically 2–3× fewer billed hosts.

Developers get full observability

SigNoz in dev means developers see traces, metrics, and logs locally — not just log lines.

Production-grade tooling kept

Datadog's incident timeline, SLO tracking, anomaly detection, and mobile app remain for on-call.

Rails Instrumentation — Same for All Options

// Gemfile

# Gemfile
gem 'opentelemetry-sdk'
gem 'opentelemetry-exporter-otlp'
gem 'opentelemetry-instrumentation-all'  # auto-instruments Rails, ActiveRecord, Redis, Sidekiq…

// config/initializers/opentelemetry.rb

require 'opentelemetry/sdk'
require 'opentelemetry/exporter/otlp'
require 'opentelemetry/instrumentation/all'

OpenTelemetry::SDK.configure do |c|
  c.service_name    = ENV.fetch('OTEL_SERVICE_NAME', 'rails-app')
  c.service_version = ENV.fetch('OTEL_SERVICE_VERSION', '1.0.0')
  c.use_all   # Rails, Action Pack, Active Record, Net::HTTP, Faraday, Redis, Sidekiq
  c.add_span_processor(
    OpenTelemetry::SDK::Trace::Export::BatchSpanProcessor.new(
      OpenTelemetry::Exporter::OTLP::Exporter.new(
        endpoint: ENV.fetch('OTEL_EXPORTER_OTLP_ENDPOINT', 'http://otel-collector:4317')
      )
    )
  )
end

Migration Path — No Hard Cutover
01

Parallel run — validate new stack

Run new and old pipeline simultaneously. OTEL Collector tails the existing log file alongside Logstash.

Deploy new stack (Grafana OSS or SigNoz) alongside existing
Configure OTEL Collector filelog receiver to tail production.log
Verify logs appear correctly in Loki or SigNoz
02

Add Rails OTEL instrumentation

Add opentelemetry-ruby gems. Rails now sends OTLP directly — traces and metrics appear for the first time.

Add gems, deploy initializer, set OTEL_EXPORTER_OTLP_ENDPOINT env var
Confirm traces, metrics, and logs all arrive in new stack
Build dashboards and alerts in Grafana or SigNoz
03

Decommission old pipeline

After 30 days of parity, shut down Logstash and Elasticsearch. What happens to Datadog depends on your chosen option.

Stop and remove Logstash and Elasticsearch containers (all options)
Options A & B: cancel Datadog subscription entirely
Option C: keep Datadog for production, remove from dev/staging only
Recover 5–11 GB RAM — downsize EC2 instance if appropriate

Which to Choose

// Option A (Grafana OSS)

  • Team knows Grafana / PromQL
  • Widest OSS community
  • S3 retention for logs + traces
  • Grafana Cloud upgrade path
  • Adding Pyroscope profiling later

// Option B (SigNoz)

  • Lowest operational complexity
  • No Grafana expertise needed
  • Trace-to-log correlation built-in
  • ClickHouse storage efficiency
  • Fastest time to observability

// Option C (Hybrid)

  • Datadog required for production
  • Want to cut non-prod Datadog fees
  • Devs need full observability locally
  • Keep production incident tooling
  • Best cost/capability trade-off
